## 쿠키

쿠키란 웹사이트가 브라우저에 맡겨 두는 작은 메모(이름=값 형태의 문자열)다.

브라우저는 쿠키를 도메인별로 보관하고, 그 사이트에 요청을 보낼 때마다 조건(Domain, Path, Secure, SameSite 등)에 맞는 쿠키를 자동으로 같이 보낸다.

쿠키는 1994년 넷스케이프(Netscape)의 루 몬툴리(Lou Montulli)가 만들었다. 처음에는 온라인 쇼핑몰의 장바구니 정보를 기억하기 위한 용도였다.

- 쿠키 하나는 약 4KB(이름 + 값 기준)까지만 저장할 수 있고(도메인당 개수 제한도 있다), 매 요청마다 함께 전송되므로 큰 데이터는 localStorage 등에 저장하는 것이 낫다.

### 쿠키가 필요한 이유

웹의 기본 통신 방식인 HTTP는 상태가 없다(stateless).

서버 입장에서 받은 모든 요청은 매번 새로운 요청이 되며, 로그인한 사람이 다른 페이지로 이동하더라도 같은 사람의 요청인지 구분하지 못한다.

쿠키를 쓰면 서버가 처음 응답할 때 식별값(예: 세션 ID)을 브라우저에 맡기고, 이후 요청마다 브라우저가 그 값을 돌려보내므로 서버가 "같은 사람"임을 알 수 있다.

### 쿠키 생성 방법

**`서버측에서 응답 헤더로 만들기`**

서버 응답 예시

```text
HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; Path=/; HttpOnly; Secure
```

- 쿠키 하나당 `Set-Cookie` 헤더 하나를 쓴다. 여러 개를 만들려면 `Set-Cookie` 헤더를 여러 번 보낸다.

브라우저는 해당 쿠키 정보를 받아 저장하고, 이후 같은 사이트로 요청할 때마다 `Cookie` 헤더에 붙여 보낸다.

```text
GET /mypage HTTP/1.1
Cookie: session_id=abc123; utm_source=facebook
```

- `utm_source=facebook`은 아래 JS 예시로 만든 쿠키다. 서버가 만든 쿠키와 JS로 만든 쿠키는 구분 없이 함께 전송된다.
- 서버 요청 헤더에 Path, Secure 같은 속성이 없는 이유는 속성은 브라우저에게 "언제, 어디로 보낼지"를 알려주는 규칙이기 때문이다. 브라우저는 그 규칙으로 보낼 쿠키를 고른 뒤, 서버에는 `이름=값`만 보낸다. 그래서 서버는 요청만 보고 쿠키의 만료일이나 속성을 알 수 없다.

**`JS로 만들기`**

```js
document.cookie = 'utm_source=facebook; path=/; max-age=604800'; // 604800초 = 7일
```

- JS로는 `HttpOnly` 쿠키를 만들 수 없다. `HttpOnly`는 서버의 `Set-Cookie`로만 설정할 수 있다.

### 쿠키 기본 속성

| 속성              | 역할                                                                                                                                                                   |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Expires / Max-Age | 만료 시점. `Expires`는 날짜, `Max-Age`는 초 단위이며 둘 다 있으면 `Max-Age`가 우선한다. 둘 다 없으면 세션 쿠키로 동작한다(탭이 아니라 브라우저를 종료할 때 삭제).      |
| Domain            | 쿠키를 보낼 도메인. 지정하면 그 도메인과 모든 서브도메인으로 전송되고, 생략하면 쿠키를 만든 호스트에만 전송된다.                                                       |
| Path              | 쿠키를 보낼 URL 경로. `Path=/shop`이면 `/shop`, `/shop/item` 요청에는 보내고 `/mypage` 요청에는 보내지 않는다.                                                         |
| Secure            | HTTPS 요청에만 전송한다. HTTP 페이지에서는 `Secure` 쿠키를 만들 수 없다(localhost는 예외).                                                                             |
| HttpOnly          | JS(`document.cookie`)로 읽거나 수정할 수 없게 한다. 요청에는 정상적으로 전송된다. XSS 공격으로 세션 쿠키를 탈취당하는 것을 막기 위해 로그인 세션 쿠키에 주로 사용한다. |
| SameSite          | 다른 사이트에서 시작된 요청(cross-site)에도 쿠키를 보낼지 결정한다. 값이 없으면 Chrome·Edge 등 크로미움 브라우저는 `Lax`로 취급한다.                                   |

- SameSite의 "사이트"는 도메인보다 넓은 개념이다. `www.xtool.co.kr`과 `m.xtool.co.kr`은 도메인은 다르지만 같은 사이트(`xtool.co.kr`)로 본다.

**`SameSite 옵션`**

| 옵션   | 설명                                                                                                                                                                               |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Strict | 같은 사이트에서 시작된 요청에만 보낸다. 다른 사이트의 링크를 클릭해 들어온 첫 요청에도 보내지 않으므로, 로그인 쿠키에 쓰면 외부 링크로 들어왔을 때 로그아웃된 것처럼 보일 수 있다. |
| Lax    | 다른 사이트의 링크를 클릭해 페이지를 이동하는 요청(최상위 이동 + GET)에는 보낸다. 다른 사이트에 삽입된 이미지·iframe·fetch 요청이나 POST 폼 전송에는 보내지 않는다.                |
| None   | 다른 사이트에서 시작된 요청에도 항상 보낸다. 반드시 `Secure`와 함께 써야 하며, 없으면 브라우저가 쿠키를 거부한다.                                                                  |

**`Domain 특이사항`**

값이 없으면 쿠키를 만든 정확한 호스트에서만 사용된다.

예를 들어 `Domain=xtool.co.kr`로 설정하면 `www.xtool.co.kr`, `m.xtool.co.kr` 등 모든 서브도메인에서 공유되지만, 값이 없으면 쿠키를 만든 호스트(예: `www.xtool.co.kr`)에서만 사용된다.

- 앞에 점을 붙인 `Domain=.xtool.co.kr`은 예전 방식이며, 지금은 점을 붙이지 않아도 서브도메인까지 포함된다.
- 현재 페이지의 호스트를 포함하지 않는 도메인으로는 쿠키를 만들 수 없다. 예를 들어 `www.xtool.co.kr`에서 `Domain=naver.com`은 거부된다.
- `co.kr`, `com`처럼 누구나 도메인을 등록하는 공개 접미사(Public Suffix)도 Domain으로 지정할 수 없다.

서브도메인 공유를 위해 `Domain=xtool.co.kr`로 고정해 두면 localhost 같은 테스트 환경에서는 쿠키 저장이 거부된다. 현재 호스트(`localhost`)가 `xtool.co.kr`에 포함되지 않기 때문이다.

- 해결: 개발 환경에서는 Domain을 생략하거나, hosts 파일에 `local.xtool.co.kr`처럼 서브도메인을 등록해 테스트한다.

### JS Cookie API(document.cookie) 특징

| 특징                            | 설명                                                                                                                                                                                                |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 읽으면 문자열 하나로 반환       | `document.cookie`를 읽으면 `"a=1; b=2; c=3"`처럼 모든 쿠키가 하나의 문자열로 나온다. 특정 쿠키를 꺼내려면 `; `로 잘라서 직접 파싱해야 한다.                                                         |
| 대입해도 전체가 덮어써지지 않음 | `document.cookie = 'a=1'`은 쿠키 전체를 바꾸는 것이 아니라 쿠키 하나를 추가하거나 수정한다. 이름·Domain·Path가 모두 같아야 기존 쿠키가 수정되고, 하나라도 다르면 같은 이름의 쿠키가 하나 더 생긴다. |
| 속성을 못 읽음                  | 읽을 때는 `이름=값`만 나오고 만료일·Domain·Path 같은 속성은 알 수 없다. `HttpOnly` 쿠키는 목록에 아예 나오지 않는다.                                                                                |
| 삭제 함수가 없음                | 같은 이름·Domain·Path로 `max-age=0`(또는 지난 날짜의 `expires`)을 설정해서 만료시키는 방식으로 삭제한다. Domain·Path가 다르면 삭제되지 않는다.                                                      |
| 특수문자 인코딩 주의            | 값에 `;`, `,`, 공백 등이 들어가면 쿠키가 잘리거나 깨진다. 저장할 때 `encodeURIComponent()`, 읽을 때 `decodeURIComponent()`를 사용한다.                                                              |

```js
// 읽기
const getCookie = (name) =>
	document.cookie
		.split('; ')
		.find((row) => row.startsWith(name + '='))
		?.split('=')[1];

// 삭제 (만들 때와 같은 path로 지정)
document.cookie = 'utm_source=; path=/; max-age=0';
```

### first / third party 쿠키 구분

| 구분             | 설명                                                                                                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| first-party 쿠키 | 사용자가 주소창에서 보고 있는 사이트와 같은 사이트의 쿠키. 예: `xtool.co.kr`에 방문했을 때 `xtool.co.kr`이 만든 로그인·장바구니 쿠키, 사이트에 설치한 GA4가 JS로 만든 `_ga` 쿠키                 |
| third-party 쿠키 | 보고 있는 사이트가 아닌 다른 사이트의 쿠키. 페이지에 삽입된 광고·픽셀·iframe 등이 자기 도메인으로 요청을 보낼 때 사용된다. 예: `xtool.co.kr` 페이지에 삽입된 광고 서버(`doubleclick.net`)의 쿠키 |

- 쿠키 자체에 first/third 구분이 있는 것이 아니라, **어떤 사이트를 보고 있을 때 사용되느냐**로 결정된다. `facebook.com`의 쿠키는 facebook.com에 방문했을 때는 first-party, 다른 쇼핑몰 페이지에 삽입된 Facebook 버튼에서 사용될 때는 third-party다.
- third-party 쿠키는 여러 사이트에서 같은 사용자를 알아볼 수 있어서, 사이트를 넘나드는 행동 추적(리타게팅 광고 등)에 사용되어 왔다.

**`서드파티 쿠키 주의점`**

- 브라우저마다 정책이 다르다.
  - Safari: ITP로 서드파티 쿠키를 기본 차단한다(2020년 Safari 13.1부터 전면 차단).
  - Firefox: 기본 설정(Total Cookie Protection)에서 서드파티 쿠키를 사이트별로 분리 저장해, 다른 사이트에서 같은 쿠키로 사용자를 추적할 수 없게 한다.
  - Chrome: 서드파티 쿠키를 폐지하려던 계획을 철회해, 현재는 기본적으로 허용한다(사용자가 설정에서 차단할 수 있음).
- 서드파티 쿠키로 보내려면 반드시 `SameSite=None; Secure`로 설정해야 한다. SameSite 값이 없으면 Chrome에서 `Lax`로 취급되어 다른 사이트에 삽입된 요청에는 전송되지 않는다.
- 그래서 광고·분석 도구들은 서드파티 쿠키 대신 **광고주 사이트의 도메인에 first-party 쿠키를 만드는 방식**으로 바꾸고 있다. 예: Meta 픽셀의 `_fbp`, GA4의 `_ga`는 광고주 사이트의 JS가 만든 first-party 쿠키다. 다만 JS로 만든 쿠키이므로 Safari에서는 7일 제한을 받는다. ([Safari 브라우저 정책 주의](#utm과-쿠키) 참고)
- 브라우저 쿠키에만 의존하지 않도록 서버에서 직접 전환 데이터를 보내는 방식(Meta 전환 API(CAPI), GA4 Measurement Protocol 등)을 함께 사용하는 경우가 많다.

## UTM - Urchin Tracking Module

UTM은 링크 끝에 붙이는 추적용 꼬리표(쿼리 파라미터)다. 핵심 역할은 어떤 링크를 통해 사이트에 들어왔는지 분석 도구가 알 수 있게 해주는 것이다.

```text
https://example.com/landing?utm_source=facebook&utm_medium=paid_social&utm_campaign=f2_launch
```

UTM은 링크를 제작하는 사람이 직접 출처를 적어 넣는 방식으로, 세부적인 유입 경로를 추적할 수 있게 해준다.

- 브라우저가 자동으로 붙여주는 정보가 아니므로, 링크를 만들 때 UTM을 붙이지 않으면 추적되지 않는다.

**`Urchin`**

Urchin은 구글이 2005년에 인수한 웹 분석 회사 이름이다.

Urchin 회사 제품이 구글 애널리틱스(현재 버전은 GA4)의 전신이라서 이름이 그대로 남아있다.

### UTM이 필요한 이유

**`브라우저 헤더의 한계`**

브라우저는 요청을 보낼 때 Referer 헤더에 이전 페이지 주소를 담아 어디서 왔는지 알려주지만 한계가 있다.

- HTTP 헤더 이름은 초기 표준 문서의 오타가 그대로 굳어져 `Referer`(r 하나)로 쓴다. 관련 정책 헤더는 `Referrer-Policy`(r 둘)로 표기가 다르다.

| 문제           | 설명                                                                                                                                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 유입 경로 한계 | 카카오톡, 문자, 이메일, 앱, PDF에서 누른 링크는 Referer가 전송되지 않아 출처가 남지 않고 '직접 유입(direct)'으로 잡힌다.                                                                             |
| 상세 경로 한계 | 브라우저 기본 정책(`strict-origin-when-cross-origin`)상 다른 사이트로 이동할 때는 전체 URL이 아니라 도메인(origin)만 전달된다. 유입 사이트를 알더라도 어느 광고인지, 어느 캠페인인지 파악할 수 없다. |

### 기본 UTM 파라미터 종류(컨벤션)

| 파라미터     | 의미        | 질문                 | 예시                               |
| ------------ | ----------- | -------------------- | ---------------------------------- |
| utm_source   | 유입 출처   | 어디서?              | facebook, naver, kakao, newsletter |
| utm_medium   | 매체 유형   | 어떤 방식으로?       | paid_social, cpc, email, blog      |
| utm_campaign | 캠페인 이름 | 무슨 목적으로?       | f2_launch, black_friday_2026       |
| utm_content  | 소재 구분   | 어떤 광고 또는 버튼? | video_a, banner_top                |
| utm_term     | 키워드      | 어떤 검색어로?       | 레이저 각인기                      |

**`특징`**

| 특징                  | 설명                                                                                                                                                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 일반적 사용법         | 일반적으로 `utm_source`, `utm_medium`, `utm_campaign` 세 개는 항상 채우고, `utm_content`, `utm_term`은 필요할 때 추가한다                                                                                             |
| 대소문자 구분         | 값은 대소문자를 구분한다. `Facebook`과 `facebook`은 서로 다른 출처로 집계되므로, 소문자와 `_` 같은 규칙을 정해 일관되게 쓴다                                                                                          |
| GA4 채널 자동 분류    | GA4는 `utm_medium` 값을 보고 채널(Paid Social, Email 등)을 자동 분류한다. `cpc`, `email`처럼 널리 쓰는 값을 사용해야 채널이 올바르게 잡힌다                                                                           |
| 한글 또는 공백 인코딩 | 한글이나 공백은 URL에 그대로 넣을 수 없어 퍼센트 인코딩된다. (예: `레이저 각인기` → `%EB%A0%88%EC%9D%B4%EC%A0%80%20%EA%B0%81%EC%9D%B8%EA%B8%B0`) 링크를 직접 조합할 때는 `encodeURIComponent()`나 URL 빌더를 사용한다 |

### First touch / Last touch

UTM으로 수집한 유입 경로 데이터를 전환(신청, 구매 등)에 연결할 때, 어떤 채널에 성과를 돌릴지에 따라 first touch / last touch 방식으로 나뉜다. 이처럼 성과를 채널에 나눠 주는 규칙을 기여 모델(attribution model)이라고 한다.

| 방식        | 설명                                             |
| ----------- | ------------------------------------------------ |
| first touch | 처음 데려온 채널에 공을 돌리는 방식              |
| last touch  | 신청(전환) 직전에 들어온 채널에 공을 돌리는 방식 |

예: 사용자가 페이스북 광고로 처음 방문하고, 일주일 뒤 네이버 검색 광고로 다시 들어와 신청했다면

- first touch → 페이스북의 성과
- last touch → 네이버의 성과
- first touch는 "어떤 채널이 새로운 고객을 발견하게 했는가", last touch는 "어떤 채널이 최종 결정을 이끌었는가"를 보는 데 적합하다.

first / last touch 방식을 둘 다 사용할 경우 first_utm\_... / last_utm\_... 방식의 네이밍 컨벤션을 사용한다.

- (예: `first_utm_source`, `last_utm_source`)

### 실무에서 자주하는 실수

**`사이트 내부 링크에 utm을 붙이는 것`**

메인 배너에서 상품 페이지로 가는 링크에 utm을 붙이는 경우, 원래 광고 출처가 내부 링크의 utm 값으로 덮어써진다.

- 이전 버전인 유니버설 애널리틱스(UA)에서는 utm 값이 바뀌면 새로운 세션이 시작되어, 세션 수가 부풀고 광고 출처가 덮어써졌다.
- GA4에서는 utm이 바뀌어도 새 세션이 시작되지는 않는 것으로 알려져 있다. (자료마다 설명이 엇갈리는 부분이다) 하지만 세션 수와 관계없이, 이후 일어난 전환의 성과가 내부 링크의 utm(예: `utm_source=main_banner`)에 돌아가 실제로 고객을 데려온 광고의 성과가 줄어드는 문제는 그대로다.
- 직접 구현한 last touch 저장 로직(아래 UTM과 쿠키 참고)도 내부 링크의 utm으로 덮어써진다.

따라서 내부 클릭 추적은 utm 대신 이벤트로 해야 한다. (예: GA4의 `select_promotion` 이벤트나 직접 정의한 클릭 이벤트)

**`redirect에서 utm이 사라지는 것`**

단축 URL, 또는 http -> https, www 유무 리다이렉트를 거치면서 쿼리가 누락되는 경우가 있다.

- 리다이렉트 자체가 쿼리를 지우는 것이 아니라, 서버의 리다이렉트 규칙이 원래 쿼리를 새 주소에 붙여주지 않게 설정되어 있으면 사라진다.

링크 생성시 실제로 테스트하여 최종 주소에 utm이 남는지 확인하는 것이 좋다.

**`utm을 # 뒤에 붙이는 것`**

`https://example.com/#/landing?utm_source=naver`처럼 해시(`#`) 뒤에 붙은 값은 쿼리 파라미터가 아니라 프래그먼트다. 서버로 전송되지 않고, GA4도 기본 설정으로는 읽지 않는다.

- utm은 `https://example.com/landing?utm_source=naver#section`처럼 `#` 앞의 쿼리 영역에 붙여야 한다.
- 해시 라우팅을 쓰는 SPA에서 링크를 만들 때 자주 발생한다.

### UTM과 쿠키

UTM은 처음 들어온 페이지의 URL에만 붙어 있다. 사용자가 다른 페이지로 이동하거나 며칠 뒤 다시 방문하면 URL에서 UTM이 사라진다.

그래서 신청 폼처럼 나중에 일어나는 전환에 UTM을 연결하려면, 처음 들어왔을 때 UTM 값을 쿠키(또는 localStorage)에 저장해 두었다가 전환 시점에 꺼내 써야 한다.

| 방식        | 저장 규칙                                                             |
| ----------- | --------------------------------------------------------------------- |
| first touch | 저장된 값이 **없을 때만** 저장한다. 이미 값이 있으면 덮어쓰지 않는다. |
| last touch  | UTM이 붙은 링크로 들어올 때마다 **덮어쓴다.**                         |

- last touch에서 UTM 없이 들어온 방문(직접 유입)까지 덮어쓰면, 대부분의 전환이 '직접 유입'으로 잡힌다. 그래서 보통 UTM이 있을 때만 덮어쓴다.

**`Safari 브라우저 정책 주의`**

Safari는 추적 방지 기능(ITP, Intelligent Tracking Prevention) 때문에 JavaScript(`document.cookie`)로 만든 쿠키의 유효기간을 최대 7일로 제한한다.

따라서 쿠키의 만료 기간(`expires`)을 90일로 설정해도 Safari에서는 7일 뒤 사라질 수 있으므로, 오래 보관해야 한다면 서버에서 `Set-Cookie` 헤더로 쿠키를 설정하는 방법을 고려한다.

- localStorage도 이 제한에서 자유롭지 않다. Safari는 사용자가 Safari를 사용한 7일 동안 해당 사이트를 방문(상호작용)하지 않으면 localStorage, IndexedDB 등 JavaScript로 저장한 데이터를 삭제한다. (Safari 13.1부터 적용)
- 차이점: 쿠키는 "만든 시점부터 7일"이 지나면 만료되고, localStorage는 "마지막 방문부터 7일" 동안 방문이 없으면 삭제된다. 그래서 자주 방문하는 사용자라면 localStorage가 더 오래 남는다.
- Safari 17(iOS 17)부터는 링크 추적 보호(Link Tracking Protection) 기능으로, 개인정보 보호 브라우징과 메일·메시지 앱에서 연 링크의 `gclid`, `fbclid` 같은 광고 클릭 ID를 URL에서 제거한다. utm 파라미터는 제거되지 않는 것으로 확인되지만, Apple이 제거 대상 목록을 공개하지 않으므로 직접 테스트해 보는 것이 좋다.

**`저장 방식 - localstorage`**

```text
// key: touchpoint_info

// value
[{"touchpoint_url":
"https://nsprotein.com/product/detail.html
?product_no=335
&cate_no=213
&display_group=1
&utm_source=google
&utm_medium=pmax
&utm_campaign=260910_g_pmax_qwp_ndet3
&utm_content=
&utm_term=
&nbsrc=adwords_x
&nbkw=
&gad_source=1
&gad_campaignid=24241093378
&gbraid=0AAAAACVCmSQCVB5kJ8-xxxxxxxxxx
&gclid=EAIaIQobChMI_xxxx_ZlwMVSKlmAh3xXDA7EAMYASAAEgKsBfD_BwE",
"touchpoint_time":1793079952585}]
```

- 저장 구조: 방문할 때마다 `{ 유입 URL, 방문 시각 }` 객체를 배열에 쌓는 방식이다. 배열의 첫 번째 항목을 보면 first touch, 마지막 항목을 보면 last touch가 되고, 중간 경로까지 모두 남으므로 여러 접점을 함께 분석(멀티 터치)할 수도 있다.
- `touchpoint_time`: 1970년 1월 1일부터 지난 시간을 밀리초로 나타낸 Unix timestamp(`Date.now()` 값)다. `1793079952585`는 한국 시간으로 2026-10-27 14:45:52이다.
- utm 값을 따로 뽑지 않고 URL 전체를 저장한다. 그래서 utm 외의 파라미터도 함께 남는다.

| 파라미터                       | 의미                                                                                                                 |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| `utm_medium=pmax`              | 구글 실적 최대화(Performance Max) 캠페인을 뜻하도록 광고주가 정한 값                                                 |
| `utm_content=`, `utm_term=`    | 값이 비어 있다. 링크 템플릿에 파라미터만 넣고 값을 채우지 않은 경우로, 분석 시 빈 값으로 집계된다.                   |
| `gclid`                        | 구글 광고 클릭 ID. 구글 광고의 자동 태그 기능이 클릭마다 붙이며, 구글 애즈와 GA4가 클릭과 전환을 연결할 때 사용한다. |
| `gbraid`                       | iOS 환경 등에서 `gclid` 대신 쓰이는 구글 광고 클릭 측정용 파라미터                                                   |
| `gad_source`, `gad_campaignid` | 구글 광고가 자동으로 붙이는 파라미터로, 광고 출처와 캠페인 ID를 담는다.                                              |
| `nbsrc`, `nbkw`                | utm이나 구글 표준 파라미터가 아니라, 사이트나 사용하는 분석 도구가 따로 정의한 파라미터로 보인다.                    |
